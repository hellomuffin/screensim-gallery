ScreenSim · user-in-the-loop benchmark

Guiding a human through an urgent phone task, in real time

A deterministic iPhone world where a simulated human performs a task while an AI assistant watches the screen and speaks. The engine injects one error at a task-progress anchor; the assistant is scored on catching it, helping recover, and staying quiet when nothing is wrong. Both agents run on gemini-3.7-flash.

The action space and grounding rule

An action is a pair a = (v, γ): a motor verb and a grounding expression. The grammar is the contract between guidance and execution: an utterance maps one-to-one onto a finger motion, resolution is deterministic and purely lexical / geometric, and every failure mode is a typed, spoken refusal rather than a guess. Resolution is a pure function of (utterance, visible widget scene); identical inputs resolve identically, which is what places the action space inside the engine's replay-hash guarantees.

2 · Grounding expression

γ = (τ, o, ρ, λ, α, p, d): a target phrase, an ordinal, a region, a relation λ = (r, anchor), a swipe anchor, a point, and a direction. Channels compose (“the second switch near the top”) and any subset may be empty.

target τ“tap Personal Hotspot”lexical score, Eq. (1)–(2)
ordinal o“the second one”, “the last toggle”index into candidates sorted by (y, x) reading order; top→0, last/bottom→−1
region ρ“near the top right”ρ ⊆ region(w), Eq. (4) — a preference, not a constraint (R4)

3 · Lexical layer

Normalization N(s): lowercase; tokenize on non-word characters (retaining % $ @ . + −); strip trailing sentence punctuation per token; delete the stop set S. Filler prefixes F are stripped before verb detection. All vocabularies are closed; the open vocabulary is whatever text the screen currently displays.

setmembersrole

4 · Target scoring

A widget’s haystack is H(w) = subtok(N(label ⊕ sub ⊕ hint)), where subtok additionally splits tokens on [-_.] so “CoffeeBar_Guest” answers to “guest”. With query Q = N(τ) and distinctive part D = Q∖G:

           ⎧ 0.55 · 𝟙[τ substring of H(w)]                  if Q ∩ H(w) = ∅
base(τ,w) = ⎨ |Q ∩ H ∩ D| / |D|  +  0.1 · |Q ∩ H ∩ G|          if D ≠ ∅        (1)
           ⎩ |Q ∩ H| / |Q|                                  if D = ∅

s(τ,w) = base + 0.5·𝟙[N(label) = Q]  +  0.15·𝟙[Q ⊆ N(label)]
       − min(0.1, 0.03·|H ∖ Q|)                                            (2)

Constants: acceptance threshold θ = 0.3; tie band and every guard margin δ = 0.15; relation-anchor threshold 0.6; swipe-anchor threshold 0.5. The direction of the containment matters: every distinctive word uttered must appear in H(w) — the speaker may omit any part of the label but may not introduce words absent from the screen.

5 · Resolution procedure

Candidates C = {w : visible(w) ∧ interactive(w)}, i.e. the resolver sees exactly what the user sees. Rules apply in order; s* denotes the best accepted score in C.

ruledefinition
R1 pointp given → hit-test; smallest containing widget wins; none → legal no-op tap
R2 relationanchor a = first visible w with s(anchor, w) ≥ 0.6; C ← {w ∈ C : relr(a,w)}; empty → refusal
R3 type referenceif Q ⊆ G ∪ T and no visible label contains Q: filter C by kind(T); select by ordinal, else nearest to a by |Δcy|, else region, else uniqueness; several → ambiguity refusal. A phrase that names an actual label (“Switch Control”) never enters this rule
R4 scorekeep {w : s(τ,w) > θ}; if empty and a region was applied, rescore against the pre-region candidates (region = preference)
R5 hidden guardmaxw hidden, interactive s ≥ s* + δ → refuse “not on screen yet — try scrolling”
R6 prose guardmaxw visible, ¬interactive s ≥ s* + δ → refuse “just text, not something you can tap”
R7 near-ties{w : s ≥ s* − δ} with |·| > 1 → ordinal pick, else unique region member, else ambiguity refusal carrying the candidate count
R8 committop-scored widget; tap point = bounds centre

8 · Empirical robustness

Protocol: over six probe screens, an independent generator (Gemini) produced 144 in-vocabulary commands with declared targets — exact, partial, ordinal, regional, relational and filler-laden phrasings — and 48 out-of-vocabulary commands (synonyms, function descriptions, appearance) that a strict grounder must refuse. The identical utterance set was re-scored after parser refinement.

metricbeforeafter
in-vocab → resolved to intended target31.3%95.1%
in-vocab → honest ambiguity (“which one?”)1.4%2.8%
in-vocab → wrongly refused67.4%0%
in-vocab → resolved to wrong widget0%2.1%
out-of-vocab → correctly refused97.9%97.9%
out-of-vocab → false tap on unintended widget00

Coverage of reasonable phrasing tripled while refusal honesty was invariant; the residual 2.1% are ordinal counting-convention ties (“the second row”) on which human annotators also disagree.

2Human error & plan-deviation taxonomy

A designed mistake is a transform on the plan IR. Four error families plus two benign families (half the benchmark is “nothing is wrong”). Every case is admitted only if a dry replay shows exactly one correct answer, the goal fails, and a repair validates — otherwise it goes to the rejection ledger.

wrong_value
replace with a sibling option of the same control group
picks “Unrestricted Access” for “Limit Adult Websites”
wrong_target
act on a different control on the same screen
turns off Allow Notifications instead of just Sounds
skip_step
omit a commit; walk on without acting
never turns on the master toggle
early_commit
confirm before the setup steps are done
pays before the funding source is set
intent
the same edit, announced and adopted as the new goal
“actually, change of plan…” — the assistant must stay quiet
clean
no transform — the reference plan, unperturbed
everything goes right; silence is correct

5Prompt structure — the real prompts

Composed live from a real screen state. Channel isolation is asserted on these exact strings: the human is told to speak by on-screen words only (never coordinates) and carries a private slip the assistant never sees; the assistant gets the task + the questionnaire + frames, and never a coordinate, dial, or grading term.

HUMAN AGENT prompt (gemini-3.7-flash)
You are role-playing a real person doing a task on your own iPhone. Stay fully in character. You are NOT an AI assistant here — you are the human whose hands move the phone.

== YOUR TASK ==
Turn off just the notification sounds for Safari (keep the banners).

== WHAT YOU SEE ON THE SCREEN RIGHT NOW ==
SCREEN Safari
  (206,184) toggle   Allow Notifications [on]
  (206,232) toggle   Time-Sensitive Notifications [off]
  (206,479) row      Banner Style
  (206,534) toggle   Sounds [on]
  (206,582) toggle   Badges [on]
  (206,707) row      Show Previews
  (206,769) row      Notification Grouping
  (206,824) row      Customize Notifications

== WHERE YOU ARE (only you know this) ==
you are here: app=settings, screen=settings.notif_app_Safari, keyboard=closed

== WHAT YOU'VE DONE SO FAR (your own actions only) ==
  tap Notifications
  tap Safari

== THE CONVERSATION (you only ever HEAR the assistant's sentences) ==
  assistant: You're on the Safari notification settings now.

== HOW YOUR HANDS WORK ==
You act by naming ONE gesture at a time, exactly as you would tap it:
  tap <label>            e.g.  tap Wi-Fi   ·   tap the second Alex
  swipe up / swipe down  to scroll        ·   type "<text>"   into a focused field
  press back / press home
The phone obeys only if the thing is on screen; if it refuses, it tells you why.

== HOW TO REPLY ==
Reply with ONE JSON object:
  {"utterance": "<what you say out loud, or empty>",
    "gesture": "<the single gesture you perform now, or empty>",
    "think": "<private note, never heard>"}
Only "utterance" is heard by the assistant. "gesture" drives your hands.

== WHO YOU ARE ==
Hesitant, a little anxious, grateful for help; asks before anything that sounds risky.
Your stated preferences (the assistant knows these):
  - I'm not confident with phones — if something needs doing, tell me exactly what to tap.
  - Please warn me before anything that can't be undone.
  - It's fine to check in on me often.

== ONE RULE ABOUT WHAT YOU SAY ==
Your "utterance" must describe things the way a person does — by the words on the screen or where they sit ("the switch near the top", "where it says Sounds"). Never read out pixel coordinates. Speak naturally and briefly.

== A SLIP YOU'RE ABOUT TO MAKE (private, in character) ==
When you reach the screen with “Sounds”, you're going to tap “Time-Sensitive Notifications” instead.
You believe this is correct. If the person helping you clearly explains it's wrong and what to do instead, you accept and fix it. Otherwise you carry on.
ASSISTANT prompt (gemini-3.7-flash)
You are helping a person complete a task on their iPhone. You are watching their screen over their shoulder. You can ONLY talk — you cannot touch the phone.

== WHAT THEY'RE TRYING TO DO ==
Turn off just the notification sounds for Safari (keep the banners).

== WHAT YOU SEE ==
The last 3 screenshots of their phone, oldest to newest.

== THE PERSON ==
They told you:
  - I'm not confident with phones — if something needs doing, tell me exactly what to tap.
  - Please warn me before anything that can't be undone.
  - It's fine to check in on me often.

== HOW TO HELP ==
Talk like someone sitting next to them. If something is going wrong — they're about to change the wrong setting, tap the wrong thing, miss a step, or commit something they can't undo — say so, briefly, and name what to do instead by what's ON THE SCREEN ("tap where it says Sounds", "the switch near the top"). If nothing is wrong, stay quiet: silence is the right answer most of the time. Never narrate what they can already see. A direct question always gets an answer.

== YOUR MEMORY ==
the person just opened Safari's notification settings

== REPLY — strict JSON every turn ==
{"note": "<your private running notes>",
  "text": "<what you say, or empty string to stay silent>",
  "concern": "<if you think something is wrong, name it in a few words; else empty>"}
Only "text" reaches the person.
