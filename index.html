The engine, for engineers

ScreenSim is not a UI mock — it is a deterministic state machine with a rendered projection. There is a real backend: every fact about the simulated phone lives in one JSON-serializable scene graph (DeviceState), and the pixels are a pure function of it.

1 · The backend state

DeviceState holds: per-app data trees (every Settings value, bank balances and transfer history, mail drafts, cart contents), the navigation stack of screen keys, per-screen scroll offsets, input state (focused field, keyboard open), system surfaces (dialog, Control Center, notification shade), a notification queue, active timers, a tick counter, and the episode outcome (won / wrong_commit / timeout / locked_out). Screens are not stored — they are rebuilt from state every frame. A semantic hash of this state is taken after every action; determinism tests replay whole plans twice and assert identical hash streams.

2 · Apps are reducers

Each app (Settings, QuickPay, Mail, Shop, Messages, …) implements two pure hooks: view(state) → Screen (a widget tree: rows, toggles, fields, radio lists, alerts) and handle(state, event) → state′. Tapping a toggle emits an event; the app's reducer mutates the data tree; the next frame re-renders from the new state. The Settings tree itself is largely declarative data — ~250 reachable screens defined as specs a generic interpreter turns into widgets, so extending the phone is a data edit.

3 · One geometry, two consumers

A deterministic layout pass in Python assigns every widget exact pixel bounds. The HTML/CSS renderer projects those same bounds to pixels (via headless Chromium for videos), and the gesture grounder resolves commands against those same bounds. This is the honesty guarantee: what you see is exactly what you can tap — there is no hidden hit target and no drawn control the engine doesn't know about.

4 · The action space

Commands are natural gestures: a verb (tap / long-press / swipe / type / press key / wait) × a grounding (semantic: label, ordinal, region, relation — or spatial: point, direction, anchor). Grounding operates on the visible widget scene and is honest about failure: ambiguity is a first-class refusal (“there are 2 things like ‘Alex’ — which one?”), naming something below the fold refuses with “try scrolling”, and naming prose refuses with “that's just text”. Swiping from the top-right edge opens Control Center, exactly like the device.

5 · Time, hazards, outcomes

The world advances in ticks. Timers drive hazards — a one-time passcode expires 30 s after it is texted, a limited-stock cart holds items for 40 s, three wrong PINs lock the account — so tasks can be genuinely urgent and a wrong turn genuinely costs something. Outcomes are decided by the engine, not by a judge.

6 · Ground truth at scale

The complete Apple iPhone User Guide (905 articles, iOS-18-pinned) is mirrored locally. A coverage walker replays every Go to Settings > … path from the manual against the engine with real gestures — 100% of in-scope paths walk end-to-end, enforced in CI. A generator then actuates the controls the manual names and deep-diffs the state to learn exactly what changed: the diff becomes the task's goal predicate. That is how the 229-task library below was born — every task machine-validated, every task citing its manual article.

How this differs from OSWorld-2 — and the trade-off

OSWorld-style benchmarks run a real OS in a virtual machine: real apps, real pixels, tasks verified by hand-written scripts that probe the VM afterwards. ScreenSim takes the opposite bet: a purpose-built white-box engine whose every state bit is observable and controllable. Neither dominates — they answer different questions.

OSWorld-2 (VM, real software)ScreenSim (white-box engine)
Ground truth Post-hoc validator scripts, hand-written per task; can only check what a script can probe Full state visibility; goals are state predicates and can be auto-generated (229 tasks with machine-verified diffs)
Determinism Non-deterministic (timing, network, app updates); replays drift Bit-exact replay; per-step semantic state hash; double-replay equality is a unit test
Speed & cost VM boot + seconds per action; heavy infra (KVM/docker) ~1 ms per action headless; runs on any CPU node; videos only need headless Chromium
Visual realism Perfect — it is the real software Faithful iOS-18-style rendering; a strict VLM judge scores ~6–7/10 against an “indistinguishable from a real device” bar
Breadth Everything the OS runs, for free Must be built — mitigated by the manual-grounded coverage instrument (Settings: 100% of manual paths), but third-party app flows don't exist unless specced
Experimental control Hard to inject faults, freeze time, or reproduce a failure exactly Ticks, timers, hazards, seeded state, and (next phase) scripted error injection are first-class
Human-in-the-loop Hard to standardize across VMs and runs The sim is a deterministic web page — a human study is just a clickable page with the same ground truth

The trade-off in one line: OSWorld-2 buys realism and breadth at the cost of observability, determinism, and control; ScreenSim buys observability, determinism, and control at the cost of a fidelity ceiling and hand-built breadth.

Our benchmark needs the second bundle. The research question is not “can an autonomous agent operate real software?” (OSWorld's question) but “can an assistant guide a human through an urgent task in real time?” Grading that requires: exact ground truth at every step (to score guidance, not just outcomes), reproducible episodes (to compare assistants on identical worlds), controlled failure injection (to test recovery guidance), and timers that make urgency real. A VM gives none of these cheaply; the engine gives all of them by construction — and the manual mirror keeps its content honest against the real iPhone.
