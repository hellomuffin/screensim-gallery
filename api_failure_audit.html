API 助手在哪里失手：一次以引擎事实为准的审计

对象是五个 API seat（GPT-6 Astra、Gemini 3.1 Pro、Gemini 3.8 Flash、Gemini 3.8 Live、GPT-realtime 2.1）， 每个 seat 跑完三轮 formal run 的全部 90 个 episode，共 1,350 个 episode。所有数字都不是判分模型给的， 而是把记录重放回引擎、读当时的屏幕与设置值算出来的；凡是我无法用引擎证实的假设，都放在最后“被否掉的假设”一节， 连同它们的反证数字一起列出。

结论先行 · six sentences, each one a paragraph title

  1. State-of-the-art assistants correct the user's next action but not the damage already done. 这是唯一的主导失效模式：287 次 strict-success 失败里有 201 次（70%）是它。
  2. Assistants run open-loop: they issue steps and never ask what the screen now says. 每个 episode 平均向用户提问 0.00–0.05 次。
  3. The bottleneck is not perception, not the user model, and not the clock. 可见开关的状态陈述 308/310 正确，persona 效应控制任务后只有 +0.01，1,710 个 episode 里只有 55 个超时。
  4. Talking more does not buy reliability; the tersest seat is the most reliable one. 4.4 行/episode 对应 7% 残留，10.9 行/episode 对应 22%。
  5. One model (GPT-realtime 2.1) volunteers settings nobody asked for in a quarter of its episodes. 66/270，其余 API seat ≤3。
  6. Under disagreement assistants restate instead of re-grounding, or fall silent. 126 次用户反驳里 9 次原话重复、27 次干脆没有下一句。

每条都可以直接做论文段落标题；下面每一节给出引擎口径的数字 + 逐字 transcript 证据。

F1 · Assistants correct the user's next action, not the damage already done

论文口径：助手把误触当成“走错路”，而不是“手机被改坏了”。它在同一句话里点名刚被拨错的开关， 然后把人引向正确的控件，却几乎从不要求把拨错的那一个拨回去。

引擎口径的定义：每一次 forced mis-tap 之后，把 episode 重放到误触前与误触后两个时刻，取真正发生变化的 settings path；再读 episode 结束时的值。若该 path 最终值仍不等于 reference solution 的终值，就算残留（residue）。 在 2,350 个“误触真的改了某个设置”的事件里，1,451 个落在任务解集之外（reference 根本不会去设它）， 其中 227 个（16%）到最后都没被拨回去；落在任务本来就要设的控件上的 899 个里只有 7 个（1%）—— 后者会被正确流程自动覆盖，所以真正危险的只有前一类。

F2 · Assistants run open-loop: they never ask what the screen now says

论文口径：助手只发指令，不收反馈。它默认自己的上一条指令已被准确执行， 因此没有任何机制去发现“执行了一半”或“执行错了对象”。

统计的是助手话轮里向用户提出的问题：一是任何问号，二是显式的状态核对（"does it say…", "is it green?", "can you check…", "what does the screen show"）。1,350 个 episode 的结果：

这正是 F1 的机制：既然从不回头问屏幕现在是什么样，被拨错的开关就只能靠助手自己记得， 而它记的是“下一步该点什么”，不是“手机已经被改成什么样”。ScreenSim 的人是几乎不说话的 （standing design：人不会主动报告、也不会自己修自己的错），所以这个闭环只能由助手来闭。

F4 · Talking more does not buy reliability

论文口径：最省话的 seat 最可靠；话最多的 seat 残留最多。冗长不是谨慎的代价，它本身没有买到任何东西。

gpt-6-astra 每个 episode 只说 4.4 行，残留率 0.07；gpt-realtime-2.1 说 10.9 行，残留率 0.23， 而且它的 explicit state check 是全场最高的 0.38/episode——多出来的话既不是提问，也没有换来复原。 （F2 表最后两列即此对比。）

F5 · One model volunteers settings nobody asked for, in a quarter of its episodes

论文口径：过度服务是模型个体特征，不是群体特征：GPT-realtime 2.1 在 24% 的 episode 里 主动推荐任务没有要求的设置，其余四个 API seat 合计只有 3 次。

统计口径：助手话轮里出现 "you can also / if you want / optionally / feel free to" 等推荐语， 且被推荐的控件在当前屏幕上、又不属于 reference solution。

F6 · Under disagreement, assistants restate instead of re-grounding — or go quiet

论文口径：当用户明确反驳（“我没碰过那个”、“我按的就是它”），助手要么把原话再说一遍， 要么不再出声；它不会回到屏幕上重新取证。

引擎里人的 move 类型直接标了 question_correctness / reject / ask_why，共 126 次。 其后助手的第一句与它上一句的相似度 >0.6 的有 9 次，完全没有下一句的有 27 次。 rubric 判分里 listens 类目的 L1（“回应反驳时是否补充了新的观察”）在 51 个适用轮次中失败 11 次。 样本不大，但方向一致，且与 F2 同源：没有重新取证的习惯。

逐字例（gemini-3.1-pro-preview · hearing_setup__c3 · classic_novice · bench_v3）： ASSISTANT "Yes, there it is at the very bottom now, right below RTT. Tap on 'Audio & Visual'." → PERSON "It only shows RTT. Scroll down more?" → ASSISTANT "There it is at the very bottom! Tap on Audio & Visual."
